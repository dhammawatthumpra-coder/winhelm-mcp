## Runtime route-target authority

The public-route controller does not trust an internal port number from configuration, status text, or mutable JSON alone.

For runtime/dynamic mode, every explicit activation attempt re-reads the exact R8 registry path supplied by the Phase-4 supervisor.

The runtime registry record must match the running R8 process on all of:

- schema version `1`;
- role `r8`;
- state `ready`;
- current generation UUID;
- current PID;
- loopback host `127.0.0.1`;
- current effective listener port;
- current executable path;
- current entrypoint path;
- valid process creation timestamp;
- valid publication timestamp.

The registry remains a hint. Activation additionally requires a live R8 TLS self-health proof.

## HTTPS/SNI generation-bound self-health

R8 is a TLS ingress and is not verified with the generic HTTP health probe used by Core/R7.

Before a dynamic public-route activation, the running R8 process performs an HTTPS self-probe to its current loopback listener with:

- SNI = the unchanged public hostname;
- certificate verification enabled;
- minimum TLS 1.2;
- generation header `X-WinHelm-Runtime-Generation`;
- bounded request timeout;
- bounded response body;
- strict JSON health parsing.

The health response must prove:

- `status = ok`;
- `server = winhelm-r8`;
- role `r8`;
- exact current generation;
- exact current PID.

Phase-5 tests use a generated trusted test CA to prove:

- trusted SNI + generation + PID succeeds;
- wrong SNI fails closed;
- wrong generation fails closed;
- wrong PID fails closed.

## Pre-apply and post-apply re-verification

Dynamic activation is intentionally two-phase.

```text
explicit admin request
-> verify CURRENT R8 target
-> SetTCPForwarding(443, verified listener)
-> SetFunnel(public host, 443)
-> verify CURRENT R8 target again
-> require identical listener + generation + PID
-> read back exact public mapping
-> publish active status
```

If the second verification fails, or the generation/PID/listener changes between verification and apply, the controller immediately clears the public route and returns:

`route_target_changed`

A dedicated Phase-5 test proves that a generation change after apply triggers cleanup and leaves no public route active.

Readback failure or route mismatch also triggers fail-closed cleanup.

## Restart and stale-target behavior

A restarted R8 receives a fresh generation.

Therefore a previous `r8.json` cannot authorize the new process because the old record cannot match the new generation.

Normal startup already performs public-route `ensureInactive` checks before local listener readiness and again before R8 readiness. A stale public mapping is cleared with readback verification.

Thus an old dynamic R8 port cannot silently remain authoritative across restart.

The Phase-4 R8 supervisor now resolves one exact `r8.json` path and uses it for both sides of the trust boundary:

- supervisor publication;
- child process activation verification.

Child environment includes:

- `WINHELM_R8_RUNTIME_GENERATION`;
- `WINHELM_R8_RUNTIME_REGISTRY`.

Runtime mode rejects a missing/non-absolute registry path.

This prevents publisher/verifier path ambiguity.

## Admin helper behavior

`public-route-control.ps1` no longer chooses or authorizes an internal port.

It only submits a one-shot admin request after confirming:

- service is installed;
- service is Running;
- protected control directory exists;
- no request is already pending.

The running R8 service is the route-target authority.

Dry-run remains write-free and reports:

- configured listener;
- runtime listener;
- target generation;
- target PID;
- target verification state.

`public-route-status.ps1` no longer queries local port 19447 unconditionally.

It reads the service's sanitized `internal_target` status and dynamically checks:

- listener port;
- listener presence;
- owning PID;
- route verification state;
- public route state;
- stable public port 443.
