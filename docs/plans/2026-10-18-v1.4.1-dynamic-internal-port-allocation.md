## Configuration contract

### Core

Accepted port selector:

```text
--port <1..65535|auto>
PORT=<1..65535|auto>
```

Precedence remains:

```text
CLI --port > PORT environment > legacy default 8788
```

Rules:

1. Numeric values preserve current fixed behavior exactly.
2. Absence preserves the legacy fixed default; existing installations are not silently migrated.
3. `auto` is explicit opt-in in Core Phase 1.
4. `auto` is legal only for loopback bind hosts. A non-loopback host with `auto` fails closed.
5. Setup Assistant may choose `auto` for a new eligible installation only after the integration phases are qualified.
6. Existing fixed installations remain fixed unless explicitly changed.

R7 and R8 will use equivalent component-specific `fixed|auto` semantics in their own phases. They are not redesigned in Phase 1.

## Allocation algorithm

No check-port-then-bind operation is permitted.

For auto mode:

1. Read an optional sticky preferred port as an untrusted preference hint.
2. If the hint is syntactically valid and in range, attempt the actual listener bind directly to that port.
3. If that bind succeeds, ownership is proven by the successful bind.
4. If it fails specifically because the address is unavailable/in use, retry by binding port `0` directly and let the OS select the port.
5. Any other bind failure is fatal and fail-closed.
6. Read the actual port only from the bound listener object.
7. Publish runtime state only after readiness is established.
8. Update sticky preference only after successful readiness/publication.

There is no random-number allocator and no pre-bind availability probe. Port `0` is preferred over a custom “1x,xxx range” allocator because internal ports are hidden from the user and OS allocation is race-free with respect to ownership acquisition.

## Sticky-auto semantics

Sticky state is a preference, never endpoint authority.

Proposed state:

`~/.winhelm/runtime/preferences/<role>.json`

```json
{
  "schemaVersion": 1,
  "role": "core",
  "preferredPort": 49152
}
```

Requirements:

- malformed/unreadable preference => ignore preference and bind `:0`;
- occupied preferred port => direct bind fails, then bind `:0`;
- preference is updated only after the component is verified READY;
- deleting preference changes only port reuse behavior, never public identity;
- fixed mode does not consult or mutate sticky preference.

## Verified runtime endpoint registry

Registry root:

`~/.winhelm/runtime/endpoints/`

One role record per live component, e.g. `core.json`, `r7.json`, `r8.json`.

Minimum schema:

```json
{
  "schemaVersion": 1,
  "role": "core",
  "generation": "<uuid-per-start>",
  "state": "ready",
  "host": "127.0.0.1",
  "port": 49152,
  "pid": 12345,
  "processCreatedAt": "<Win32_Process CreationDate ISO>",
  "executablePath": "<observed executable path>",
  "entrypointPath": "<observed/expected component entrypoint>",
  "publishedAt": "<ISO timestamp>"
}
```

The registry file is a discovery hint plus an attestation bundle; **the JSON record alone is never trusted**.

Publication rules:

- same-directory atomic replace;
- publish only after listener is bound and component readiness checks pass;
- a fresh UUID generation is created on every start;
- stop removes or supersedes its own generation only after proving it still owns that generation;
- crash may leave stale state; stale state must fail verification rather than be “repaired” by timestamp.

## Identity and trust model

A consumer accepts an endpoint only when every required proof succeeds:

1. schema, role, state, loopback host and port are valid;
2. PID exists now;
3. observed executable path matches persisted executable path;
4. observed process creation time matches persisted creation time using the existing fail-closed tolerance semantics;
5. the OS reports the endpoint listener is owned by that same PID;
6. process command/entrypoint identity matches the expected component identity;
7. component health/identity response reports the same role and runtime generation;
8. no field required for proof is missing or malformed.

This extends the existing tunnel identity pattern rather than inventing a separate trust model.

Cross-identity boundary rule: a privileged consumer must not accept a user-writable endpoint registry merely because it parses. It must prove OS listener/process identity and expected executable/entrypoint identity. If ACL/identity evidence cannot make that boundary trustworthy in the R8 integration phase, stop and escalate to Owner/Main Coordinator before weakening the proof.

## Startup dependency state machine

For each dependent component:

```text
CONFIGURED
  -> RESOLVING_DEPENDENCY
  -> DEPENDENCY_VERIFIED
  -> BINDING
  -> LISTENER_OWNED
  -> SELF_READY
  -> REGISTRY_PUBLISHED
  -> READY
```

Failure from any pre-READY state transitions to STOPPED/FAILED and does not publish a usable endpoint.

Consumer behavior:

```text
READ_HINT -> VERIFY_PROCESS -> VERIFY_LISTENER_OWNER -> VERIFY_COMPONENT_GENERATION -> ACCEPT
```

Any failed proof => reject endpoint and fail closed; never fall back silently to a historical port when configuration says auto.

## Crash and restart recovery

- Stale registry state is expected after abrupt termination and has no authority.
- PID reuse is rejected by process creation time.
- Port reuse is rejected by listener-owner PID plus process identity/generation.
- Restart first tries its sticky preferred port by real bind; collision falls back to `:0`.
- Downstream components re-resolve and re-verify after dependency restart; they do not cache a host/port forever.
- A consumer seeing a generation change must treat the old endpoint as invalid.

## Migration and backward compatibility

- No existing numeric port configuration is rewritten.
- Legacy no-setting Core behavior remains fixed `8788`.
- Current production launchers may continue passing `18788`, `64239`, `19447` until their controlled phases are integrated.
- Automatic mode is additive and opt-in until Setup Assistant / launcher integration is qualified.
- Public HTTPS `443`, hostname, public MCP URL, OAuth issuer, redirect URIs, client identity and scopes are out of scope for dynamic port allocation.

## Rollback

Rollback is simple because fixed paths are preserved:

1. configure/pass the former explicit numeric port;
2. stop using endpoint discovery for that component;
3. ignore/delete dynamic runtime endpoint and preference files only after stopping the owning generation;
4. restart the last accepted fixed topology;
5. verify public route still targets the accepted local R8 fixed endpoint and public `443` identity is unchanged.

No v1.4.0 frozen source mutation is required.
