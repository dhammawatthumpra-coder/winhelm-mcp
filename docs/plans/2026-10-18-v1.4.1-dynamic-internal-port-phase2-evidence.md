## Runtime record contract

Core auto mode publishes:

`~/.winhelm/runtime/endpoints/core.json`

Minimum record fields:

- `schemaVersion = 1`
- `role = core`
- fresh UUID generation per start
- `state = ready`
- loopback host
- actual bound port
- PID
- observed Windows process creation time
- observed executable path
- trusted entrypoint path
- publication timestamp

Publication uses the existing same-directory atomic UTF-8 writer.

`publishedAt` is metadata only and is not a trust signal.

## Trust model

`resolveVerifiedRuntimeEndpoint(...)` is the intended consumer API. It performs:

1. strict record parse;
2. role check against trusted caller expectation;
3. executable and entrypoint checks against trusted caller expectations;
4. Windows process existence check;
5. PID + process creation-time proof;
6. observed executable-path proof;
7. observed process command-line entrypoint proof;
8. exact TCP listener address/port ownership by the same PID;
9. live `/health` response;
10. health role + generation + PID equality.

Any missing, malformed, stale, mismatched, or unavailable proof returns no verified endpoint.

The JSON record alone never authorizes an endpoint.

## Windows observation

Default observation uses a non-interactive Windows PowerShell child to query:

- `Win32_Process` through CIM;
- `Get-NetTCPConnection -State Listen`.

Only numeric PID/port values generated by the process are interpolated into the observation command.

Observed command line is not persisted. It is used only for current identity proof.

The entrypoint matcher accepts:

- exact absolute expected entrypoint; or
- a sufficiently specific relative suffix of at least three path components.

A generic two-component suffix such as `dist\index.js` is intentionally insufficient.

## Readiness publication

Core auto startup order is:

```text
bind listener
-> expose runtime role/generation/PID through loopback health
-> observe Windows process/listener identity
-> live health generation verification
-> atomic endpoint registry publication
-> sticky-port preference publication
-> normal READY operation
```

If verified registry publication fails:

- Core listener is stopped;
- startup throws;
- no new usable registry record is published.

Publication readiness proof has a bounded four-attempt retry with a short delay to tolerate transient Windows CIM/TCP-listener observation immediately after bind. Every attempt must still satisfy the full proof; retry does not weaken admission criteria.

## Fixed-mode compatibility

Fixed mode does not receive runtime identity projection through the main startup path and does not require the registry.

Existing fixed-port behavior remains additive/backward-compatible.
