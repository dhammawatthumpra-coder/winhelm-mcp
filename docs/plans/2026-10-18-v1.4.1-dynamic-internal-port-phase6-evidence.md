## Product-mode resolver

The new contract exposes two product modes:

`automatic | fixed`

Installation kinds:

`clean | existing`

Rules are fail-closed.

### Clean installation

If a clean install does not request another mode, recommended/default contract mode is:

`automatic`

Automatic plan:

- Core selector = `auto`;
- R7 selector = `auto`;
- R8 selector = `auto`;
- no numeric internal-port input is accepted;
- `requiresUserPortInput=false`;
- public port = 443;
- public exposure default = inactive.

### Existing installation

An existing install must supply its trusted existing internal-port mode.

The contract refuses to infer an existing mode.

If existing mode is fixed:

- preserved numeric Core/R7/R8 ports remain fixed;
- no migration occurs merely because automatic mode exists;
- changing fixed -> automatic requires `explicitModeChange=true`.

If existing mode is automatic:

- automatic remains automatic unless the user explicitly chooses fixed.

Any existing-mode change without explicit acknowledgement fails with:

`EXPLICIT_MODE_CHANGE_REQUIRED`

### Fixed mode

Fixed mode remains first-class for:

- backward compatibility;
- deterministic debugging;
- qualification;
- recovery;
- rollback.

Fixed Core/R7/R8 ports are validated to be:

- integers;
- 1024..65535;
- distinct on loopback.

A clean fixed-mode choice requires explicit fixed values.

An existing fixed install can reuse its preserved trusted values without asking the user again.

## Ordered startup and fail-closed cleanup

Reference orchestration contract:

`launchRuntimeChain(...)`

Required sequence:

```text
spawn Core
-> wait verified Core
-> spawn R7
-> wait verified R7
-> spawn R8
-> wait verified R8
-> chain ready
```

The next dependency is not started until its upstream reaches the required readiness.

If startup fails after one or more children have started, children are stopped in reverse order.

Phase-6 tests prove:

```text
Core started
R7 started
R7 readiness fails
-> stop R7
-> stop Core
-> R8 never starts
```

This contract is additive and does not replace Phase-7 crash/restart/collision qualification.

## Reference launcher CLI

Reference launcher:

`prototype/dynamic-internal-ports/launcher/start-runtime-chain.mjs`

Supported interfaces:

```text
--config=<absolute path>
--plan-only
```

`--plan-only` performs no component start.

It emits only a sanitized plan:

- mode;
- installation kind;
- migration classification;
- public HTTPS identity;
- automatic/fixed selector classification;
- executable/cwd identities;
- no raw component argument list;
- no secrets.

Run mode:

- requires R7 Gemini Client Secret only through ephemeral environment variable;
- starts Core/R7/R8 in ordered dependency sequence;
- consumes verified runtime APIs for readiness;
- emits sanitized component exit events;
- stops the chain in reverse order when a component exits or startup fails;
- does not activate the public route.

Raw child stdout/stderr is consumed but not forwarded, avoiding accidental propagation of one-time admin links, bearer material, or secret-bearing diagnostics.

## Core registry path contract

Core Phase 1 publishes only to the Core default runtime endpoint path.

The Phase-6 reference launcher therefore rejects a custom Core registry path that does not equal the Core default runtime registry.

This prevents the launcher from telling downstream R7 to consume one registry path while Core publishes another.

R7 and R8 retain their explicit registry-path parameters.
