## Shared child-endpoint publication

Phase 4 extends the Phase-2 registry publisher without creating a second trust model.

New shared API:

`publishObservedRuntimeEndpoint(...)`

It publishes an endpoint owned by a specified child PID only after the same conjunctive proof used by the current-process publisher:

1. strict role/generation/loopback/port/PID validation;
2. Windows process existence;
3. PID + process-creation-time proof;
4. observed executable-path equality;
5. command-line entrypoint proof;
6. exact listener host/port ownership by the same PID;
7. live role-specific health response;
8. health role + generation + PID equality;
9. atomic registry publication.

`publishCurrentRuntimeEndpoint(...)` now delegates to this shared implementation with `process.pid`, preserving existing Core/R7 behavior and existing error semantics.

## R8 -> R7 dependency contract

`resolveR8R7Upstream(...)` has explicit fixed and automatic modes.

Fixed mode:

- requires a loopback host;
- uses the configured numeric R7 port directly;
- does not consult the registry;
- preserves legacy fixed upstream behavior such as `127.0.0.1:64239`.

Automatic mode:

- requires trusted R7 executable and entrypoint paths;
- reads `r7.json` only as an untrusted hint;
- verifies role `r7`;
- requires the R7-specific health identity `server = winhelm-r7`;
- requires current process/listener/generation proof through the shared verifier;
- refuses R8 startup when verification fails.

A stale or forged host/port JSON value cannot authorize an R7 dependency.

## R8 listener-selection contract

The candidate R8 Go config adds optional fields:

```json
{
  "listenMode": "fixed|auto",
  "preferredPort": 0
}
```

Backward compatibility:

- omitted `listenMode` means `fixed`;
- existing `listen: "127.0.0.1:19447"` remains valid unchanged;
- fixed mode forbids `preferredPort`;
- no existing fixed installation is silently migrated.

Automatic mode:

- requires the explicit bind sentinel `listen: "127.0.0.1:0"`;
- remains loopback-only;
- an optional sticky preferred port must be within 1024..65535;
- the preferred port is acquired only by the real `net.Listen` call;
- an occupied preferred port falls back to a real `:0` bind;
- unrelated bind errors remain fatal;
- the effective listener is read from `Listener.Addr()`, never from a pre-bind availability check.

During TDD on Windows, an occupied preferred port surfaced as Winsock `WSAEADDRINUSE` / errno 10048 through `net.Listen`. The candidate now recognizes only the address-in-use class, including Windows errno 10048, as eligible for fallback. Other bind failures remain fail-closed.

There is no check-port-then-bind allocator.

## Generation-bound R8 health identity

When `WINHELM_R8_RUNTIME_GENERATION` is present, the candidate Go child validates it as a UUID and exposes a local generation-bound health response.

A successful probe must send:

`X-WinHelm-Runtime-Generation: <current-generation>`

The response identity is:

```json
{
  "status": "ok",
  "server": "winhelm-r8",
  "runtime": {
    "role": "r8",
    "generation": "<current-generation>",
    "pid": "<child-pid>"
  }
}
```

A missing or wrong generation header receives a hidden 404. Normal TLS/OAuth/MCP requests continue through the original qualified proxy handler.

This header binds the local verifier to the current generation. It is not a replacement for public authentication.

## TLS health-proof constraint for downstream consumers

Unlike Core and R7, R8 is a TLS listener.

The Phase-4 supervisor verifies R8 health using HTTPS with:

- loopback TCP target;
- SNI = the existing `expectedPublicHost`;
- certificate verification enabled;
- generation header;
- role/server/generation/PID validation.

Accordingly, Phase 5 must not blindly reuse the generic HTTP health probe intended for Core/R7. Any R8 registry consumer must use this R8-specific HTTPS/SNI proof, or an equivalently strict trusted TLS health verifier.

## R8 runtime supervisor

Candidate supervisor:

`D:\mcp\winhelm-v1.4.1-dynamic-internal-ports-r1\prototype\dynamic-internal-ports\r8\r8-runtime-supervisor.mjs`

Sequence in automatic R7-upstream mode:

```text
resolve verified R7
-> generate isolated R8 runtime config
-> create fresh R8 generation
-> launch candidate R8 child
-> wait for generation/PID-bound child readiness event
-> verify Windows process/listener identity
-> verify HTTPS/SNI generation-bound R8 health
-> atomically publish r8.json
-> update R8 sticky preference
-> report VERIFIED READY
```

If R7 verification fails, the supervisor refuses before runtime config generation and before child spawn.

If child readiness or endpoint proof fails, no usable `r8.json` is published.

R8 sticky preference is written only after registry publication and is non-authoritative.
