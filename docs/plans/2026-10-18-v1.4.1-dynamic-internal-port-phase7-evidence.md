## Collision model

Automatic allocation remains race-safe because ownership is established only by a real listener bind.

No check-port-then-bind sequence was introduced.

Phase 7 proves:

1. two simultaneous Automatic bind attempts acquire different loopback ports;
2. an occupied sticky preferred port causes the real preferred-port bind to fail and the allocator then binds port 0;
3. the unrelated process holding the sticky port is left untouched;
4. fixed mode does not fall back when its requested port is occupied;
5. R8's Go allocator preserves the same behavior.

The sticky preference remains a hint only.

It is not proof of endpoint ownership.

## Crash before registry publication

The registry publisher first proves current process/listener identity and health before writing the READY record.

Phase 7 injects a dead/unobservable process before publication.

Expected and observed result:

- publication fails closed;
- no READY registry record is produced;
- no stale fixed-port fallback is attempted.

This proves a component that dies before publication cannot leave an authoritative endpoint behind.

## Crash after registry publication

Abrupt process death after successful publication is expected to leave a stale JSON hint.

Phase 7 uses a real child process and loopback listener:

1. child starts;
2. endpoint is proven and published;
3. child is terminated;
4. registry file deliberately remains;
5. verified consumer resolution is attempted.

Observed result:

- stale JSON remains present as evidence/hint;
- verified resolution returns unavailable;
- the stale record has no runtime authority.

The design therefore does not rely on destructive cleanup to make stale state safe.

## Stale port takeover by unrelated process

Phase 7 uses two real child processes.

Sequence:

1. process A owns and publishes a verified endpoint;
2. process A exits;
3. process B binds the same former port;
4. stale process-A registry remains;
5. consumer verifies the stale record.

Observed result:

- process B is not accepted;
- listener ownership / process identity / creation-time / entrypoint proof prevents takeover;
- stale registry remains merely a rejected hint.

A numeric port alone never establishes identity.

## Duplicate process / owned-PID binding

A verified endpoint may be valid for some current process and still be wrong for the process instance that the launcher itself started.

Phase 7 adds:

`verifiedEndpointBelongsToPid(...)`

The reference launcher now requires both:

1. normal verified endpoint proof;
2. verified endpoint PID equals the launcher-owned child PID.

A second valid-looking duplicate process therefore cannot satisfy readiness for the launcher's child.

This closes a duplicate-start ambiguity without weakening endpoint verification.

## Dependency restart while downstream is alive

Phase 6 established verified startup ordering, but it did not yet automatically recover a running chain from an upstream process/generation change.

Phase 7 closes that gap conservatively.

The design deliberately does not hot-swap reviewed R7/R8 proxy internals.

Instead, Automatic mode uses full-chain lifecycle supervision:

```text
Core -> verified
R7   -> verified
R8   -> verified
CHAIN READY

if owned process exits
or verified endpoint becomes unavailable
or verified endpoint no longer belongs to the launcher-owned PID

=> stop R8
=> stop R7
=> stop Core
=> start a fresh cycle
=> re-verify Core
=> re-verify R7
=> re-verify R8
=> CHAIN RESTARTED
```

This guarantees downstream components never continue indefinitely with a cached endpoint after upstream identity changes.

Every cycle re-enters the same verified discovery gates.

## Runtime identity monitoring

While an Automatic chain is READY, the reference launcher repeatedly re-verifies:

- Core;
- R7;
- R8.

The check is not only “is a registry file present.”

Each role must still pass the verified endpoint algorithm from Phase 2 onward.

Additionally, each verified PID must equal the child currently owned by the launcher.

A process exit or identity mismatch becomes a lifecycle event and triggers conservative full-chain recovery.

## Restart budget

Automatic restart is bounded.

Reference launcher:

`maxRestarts = 3`

A persistent crash/restart storm therefore cannot loop forever.

Phase 7 tests a bounded restart budget and proves:

- each failed cycle is cleaned in reverse order;
- every new cycle starts cleanly;
- budget exhaustion returns a fail-closed terminal state.

The launcher converts budget exhaustion into an explicit runtime-chain failure.

## Signal during partial startup

The launcher now records a child in the current-started set immediately after spawn.

Therefore SIGINT/SIGTERM during partial startup can stop already-created children even before the whole chain reaches READY.

This prevents a partial Core or Core+R7 startup from becoming orphaned merely because shutdown arrived before R8 readiness.

## Fixed-mode unexpected exit

Fixed mode remains deterministic and does not use Automatic restart semantics.

If a fixed-mode component exits unexpectedly:

- the remaining current chain is stopped;
- launcher returns a failure.

A user-requested shutdown remains distinguishable from an unexpected exit.
